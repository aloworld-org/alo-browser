alo-workplace, deploy/production/downloads/index.html — alo's public page for
downloading the alomails desktop app.

Taken 2026-10-08 from the `alo-workplace` repository checked out beside this
one, at its commit 738de61401d992c9b058c83237e16c90ecbd23ef (the file's last
change is 6efc10f777b34b9ee74db0a42dceea7ae905f8ec, 2026-08-04). The bytes in
page.html are that file exactly as it stands, unedited: SHA-256
f636baa5c753f0f29670635b7c1699e98d69d8bc88533926a383063fb738aa27.
`alo-workplace` is read-only reference; nothing was written back to it.

Why this page. It is a real page alo serves to the public, not a screen
inside the workspace, and it is wholly self-contained: one inline style
sheet, one inline <svg> of the alo hand, one inline script. So it is frozen
exactly rather than rebuilt from a framework's output, and anybody can
re-derive it from the commit above. It was the first alo page left that the
corpus had not seen, and every open queue item before it was waiting for a
page, a dependency or a person (iteration 197).

**Where it is served from: `https://alomails.com/download/`** (address.txt).
`alo-workplace`'s `deploy/production/docker-compose.yml` mounts its
`downloads` directory at `/srv-downloads`, and its `Caddyfile` serves that
directory under `/download/` on `alomails.com` — and on the mail and
workspace hosts too, which change nothing here: the buttons' `href`s are
absolute paths, so they resolve to the same origin as the page either way.

**What its fetches are answered with: nothing — it is rendered offline.**
The script asks for each installer with a `HEAD` (since item 335):

- https://alomails.com/download/alomails-windows-x64-setup.exe
- https://alomails.com/download/alomails-mac-universal.dmg

The installers are built by CI into the deploy's downloads directory and
are in no repository, so there is no response here that could be frozen
with provenance, and responses.txt is absent on purpose. ADR 0032 § 7: a
fetch the case froze nothing for is a network error. So each `fetch`
rejects, its `.catch` marks the button *Building — available shortly* and
takes its `href` away — **what the page does offline, not what it does
live**, where an installer that is there leaves its button alone.
`tests/alo_downloads.rs` pins both: offline, and a server that has the
Windows installer and not the Mac one.

Rendered at 800 × 780: wider than its 560 px breakpoint, so the two cards
stand side by side, and tall enough for the whole of its content under its
6vh top padding and 40 px bottom padding. It was 760 until the card's
"Your device" badge was shown (iteration 204), which made both cards 35.86
px taller and the page 778.66.

**It is rendered as a Mac.** The script reads `navigator.platform` and
`navigator.userAgent` and marks the visitor's card, so what is drawn
depends on which system the browser says it is. The corpus states ADR
0030 § 2's macOS row for every page it loads (`alo_corpus::SYSTEM`), not
the machine running the tests, so the references are the same everywhere;
`tests/alo_downloads.rs` checks the Windows and Linux rows in the box tree.

It carries a script, so the corpus loads it through a renderer. Until
item 74 the script was refused before it ran — "a regular expression
literal is not built yet — queue item 74 builds it (at byte 144)", the
`/Mac/` in its third line. Since iteration 200 it compiles, and it stopped
at its second line instead: "ReferenceError: 'navigator' is not defined",
because no `Navigator` was built (item 325). Since iteration 203 it reads
`navigator` and finds the system in its first five lines, and since
iteration 204 (item 327) it marks that system's card `.rec` — terracotta
border and shadow — and shows its badge. Since iteration 205 (item 329)
its `document.querySelectorAll(".btn[href]")` on line 17 finds the two
download buttons. Since iteration 209 (item 331) the `.forEach(…)` called
on them is `Array.prototype.forEach`, which walks them, and the script
stopped in its first callback, at line 19: "ReferenceError: 'fetch' is not
defined". ADR 0032 (iteration 212) decided what `fetch` is, and items 333,
334 and 335 built it. Since iteration 215 (item 335) each button's fetch is
asked for, answered offline as above, and its `.catch` runs `mark(a)`:
the label becomes *Building — available shortly* and the `href` goes, so
neither button is a link any more (boxes.txt, agent.txt). Until iteration
221 it then stopped at `a.style.background = …`: "TypeError: cannot write
property 'background' of undefined", because an element's `style` was not
built (item 339). ADR 0033 (iteration 218) decided how, and items 341 and
342 built it: the write sets the button's `style` attribute to
`background: #c7bfb2;`, which is cascaded above `.btn`'s terracotta, and
the page's `cursor` and `pointerEvents` writes set ordinary properties of
the declaration, because no stage of this engine acts on either. **The
script now runs to its end**, and both buttons are drawn `#c7bfb2`
(display.txt, render.png).
`tests/alo_downloads.rs` pins that the script says nothing, which card is
marked, each button's `style` attribute and the colour it is filled with.

## What it found

- **A `<br>` did not break a line** — item 319. The note under the cards is
  three sentences separated by `<br><br>`, and all of them ran together:
  "…download it once.  Prefer the web? …" on one line, five lines in all.
  **Fixed by item 319 (iteration 198):** each `<br>` ends its line, so the
  note is eight lines, two of them blank, and 189.62 tall rather than
  125.64. `tests/alo_downloads.rs` says it in numbers.
- **`ch` is half an em** — item 320. `.lede` is `max-width: 44ch` at
  17.28 px. In DejaVu Sans a `0` is 0.636 of an em wide, so 44ch is about
  483.7 px; it is laid out 380.16 (44 × 8.64), and the paragraph wraps
  about a hundred pixels narrower than it should. `alo-text` already
  measures the face's `0`; `alo-style` still uses the stand-in its own
  comment calls an estimate, and `ex` with it.
- **Text straight inside a flex container ignores `line-height`** — item
  321. The buttons are `display: inline-flex` with their label as the only
  child, so the label is a flex item of its own rather than a line, and it
  is measured at its font's 18.625 rather than `line-height: 1.55`'s 24.8.
  Each button is 42.625 tall rather than 48.8. Iteration 196 recorded that
  this path ignores `line-height` and had not checked whether a page reached
  it. This one does.
- **The script reaches a regular expression** — item 74. Until this page no
  frozen script that runs reached one (iterations 132, 188), which is why 74
  was left alone. **Built by item 74 (iteration 200):** the whole script
  compiles, and `alo-js`'s `tests/a_frozen_page_tests_its_platform.rs` runs
  its first five lines — four patterns — under a stand-in `navigator` and
  gets `isMac` and `isWin` right for a Mac, Windows and Linux.
- **The script reads `navigator`** — item 325, opened by this page. Its
  second line is `navigator.platform || ""`, and there was no `Navigator`.
  **Built by item 325 (iteration 203):** it reads what the browser was
  told, and the next stop was `getElementById` and `classList` (item 327).
- **The script marks a card** — item 327, cut from 325. **Built
  (iteration 204):** `getElementById`, `hidden` and `classList`; the Mac's
  card is outlined and badged. The next stop was `querySelectorAll` (item
  329).
- **The script finds its buttons** — item 329, opened by this page. **Built
  (iteration 205):** `querySelectorAll` and a static `NodeList`; the two
  buttons are found. The next stop was `forEach` (item 331).
- **The script walks its buttons** — item 331, cut from 329. **Built
  (iteration 209):** `Array.prototype.forEach`, the first builtin that
  keeps state across the calls it asks for (ADR 0031), and a `NodeList`'s
  `forEach`, `keys`, `values`, `entries` and `[Symbol.iterator]` as those
  very functions. The next stop was `fetch` and `.then`: decided by ADR
  0032 (iteration 212), built by items 333–335.
- **The script asks whether each installer is there** — item 335.
  **Built (iteration 215):** `fetch` in a page, its `Response`, and the
  corpus answering a case's fetches from what it froze. Offline, both
  buttons are marked. The next stop was `a.style` — item 339, opened by
  this page: an element's `style`, whose `background`, `cursor` and
  `pointerEvents` the page sets to grey a button it has marked.
- **The script greys its buttons** — item 339. **Built (iterations 219
  and 221, items 341 and 342):** a `style` attribute is cascaded, and
  `element.style` writes it. Both offline buttons are `#c7bfb2`, and the
  script runs to its end: there is no next stop in this page's script.

Two things it asks for make no difference at this size and are not faults
here: `text-wrap: balance` on a heading that fits on one line (item 104), and
`system-ui` first in a font list (drawn in DejaVu Sans, as every case is).
The issues list names the one family it could not find, `monospace`, for
`<code>`.

The reference render pins the page as it renders today, faults included, so
that each of those items moves it and says so.
