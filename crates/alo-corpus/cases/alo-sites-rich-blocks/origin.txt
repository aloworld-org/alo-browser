## What it found

**The Rust block's indentation was gone.** `println!("alo & sites");` stood
flush with the `fn main() {` above it. `<pre>` is `white-space: pre`, and the
text arrived with its four spaces, but the line builder dropped a run of
spaces at the start of a line whatever `white-space` said. CSS Text 3
§ 4.1.2 removes only collapsible spaces there. Queue item 410, built with
this case: the line now starts four spaces in (20.34375 in DejaVu Sans then;
38.53125 in DejaVu Sans Mono since item 412).

**The code was not in a monospace face.** The user-agent sheet asks for
`monospace` and the corpus had no such face, so it was drawn in DejaVu Sans
and said so in issues.txt, as `alo-downloads` did. Queue item 412, built in
iteration 265: the corpus carries DejaVu Sans Mono and maps `monospace` to
it, the code is drawn in it, every character one 1233/2048-em advance, and
the issue is gone.

**The broken picture shows nothing.** Its `alt`, "Orange notebook <front>",
is not drawn; the `<img>` is an empty box on the figure's first line, and the
agent reads it by that `alt`. HTML's rendering section draws a broken
picture with text as that text. Queue item 413, decided by ADR 0046
(iteration 268): the `alt` becomes inline text in the `<img>`'s own style,
`width="640"` applying to it no more than it does in Chrome, and the agent
reads `image "Orange notebook <front>" [broken]`. Measured on this very page
in Chrome 154: the figure's first line holds a 16 x 16 icon and the text,
194.796875 x 18 in Chrome's sans-serif; ADR 0046 § 4 leaves the icon out, so
here the box will be the text alone. That a `data:` URL is never read as a
picture at all is item 414; here it would not matter, since these bytes are
no picture.

Rendered at 800 × 600, as the alo Sites cases are.
